口播相機
產品需求與開發規格書

給知識型、口播型新手創作者使用的極簡拍攝工具。讓不擅長拍片的人，也能自然地看著鏡頭，把想說的內容說完。

核心設計原則：複雜留給系統，簡單留給使用者。前台極簡，後台自動化；使用者不必理解攝影參數，只需要準備好內容並開始說話。

01 / PRODUCT SUMMARY

產品摘要

這不是一款功能繁多的專業相機，也不只是提詞器。它是一款新手口播拍攝助手：協助使用者完成構圖、提詞或面對鏡頭的心理準備，再以 iPhone 前鏡頭錄製影片。

核心價值 01

不會拍？幫你構圖

固定虛擬頭像框，搭配可選的臉部位置偵測。

核心價值 02

不會背？幫你提詞

整篇文字稿直接貼上，錄影時自然閱讀。

核心價值 03

怕鏡頭？陪你說話

虛擬聆聽者提供輕微、自然的非語言回饋。

產品承諾：不用背稿、不必懂構圖，也能更輕鬆地完成一支口播影片。
02 / AUDIENCE & NEEDS

目標客群與未被滿足的需求

主要客群

有專業知識、想透過短影音分享內容或經營個人品牌，但沒有拍攝習慣或不擅長面對鏡頭的人。

  • 講師、顧問、教練、老師。
  • 醫療、法律、財務等專業知識分享者（需自行遵守各行業內容規範）。
  • 寫作者、部落客、電子報作者，想把文章轉成口播。
  • 創業者、個人品牌經營者。

核心痛點

痛點產品回應
面對鏡頭不知道頭該放哪裡固定頭像／肩膀構圖框、可選臉部定位提示
怕忘詞、眼神飄移提詞文字固定在螢幕頂端（緊鄰前鏡頭）、速度可調、手動暫停
對著鏡頭感到尷尬或緊張虛擬陪伴者模式，營造視訊對話感
不懂曝光、白平衡等設定優先使用原生自動曝光、白平衡與對焦
拍錯就得整段重來快速重錄；後續可評估分段錄影
不確定收音是否正常錄影前簡單音訊輸入檢查與異常提示

市場假設需透過訪談與實際使用測試驗證；不能僅憑短影音觀看人口推論付費意願。

03 / DESIGN PRINCIPLES

產品設計原則

  1. Camera-first：打開 App 優先進入拍攝主畫面。
  2. 無感自動化：系統在背景處理可自動完成的工作，不要求使用者理解技術名詞。
  3. 零學習成本：預設值合理，第一次使用不需要先閱讀教學。
  4. 口播優先：提詞、構圖、收音與錄影穩定性優先於濾鏡、特效、剪輯。
  5. 不干擾創作：不頻繁彈窗、不在錄影中插入不必要提示。
  6. 保留使用者控制權：自動化是預設，但允許使用者關閉構圖框或調整必要設定。
  7. 隱私優先：臉部位置分析盡可能在裝置端完成，不上傳相機畫面。
「無感自動化」不等於把所有功能藏起來，而是預設替使用者做好；只有遇到需要使用者採取行動的問題，才顯示簡短、可理解的提示。
04 / TWO RECORDING MODES

雙拍攝模式

模式 A｜提詞模式

適合有稿、需要照著說的人

  • 貼上完整文字稿，不強制逐句切卡。
  • 可自動滾動，也可手動滑動。
  • 調整文字大小、速度、透明度。
  • 開始提詞前以構圖框對位；提詞開始後構圖框淡出。
  • 錄影與提詞可獨立啟動／暫停。
模式 B｜陪伴模式

適合知道要說什麼、但怕鏡頭的人

  • 不需要輸入文字稿。
  • 前鏡頭畫面搭配一位虛擬聆聽者。
  • 人物位於靠近前鏡頭的位置，避免視線偏離太遠。
  • 根據說話狀態觸發輕微點頭、眨眼與微笑。
  • 不主動說話、不打斷使用者、不理解或評判內容。

陪伴角色：先用預錄短片驗證，再決定是否投資 3D

V1 做法：預先製作同一位聆聽者的數段短片（待機 2–3 段、點頭、微笑），依說話狀態切換播放並交叉淡化。片段不含音軌。目的是用最低成本測出「有人在聽」是否真的讓使用者比較敢講。

長期視覺方向（驗證有效後才做）：選擇自然比例、略經風格化的 3D 人物：接近真人但不追求照片級寫實；眼睛自然、表情溫暖、避免誇張卡通比例。目標是親切且不詭異，而非製作一個虛擬網紅。

虛擬聆聽者（示意）
自然注視・輕微點頭・柔和微笑
角色動畫不進入最終錄影檔

陪伴效果是待驗證的產品假設。研究結果不能直接保證在手機自拍錄影情境中同樣有效，需以目標客群實測。

畫面 1：拍攝主畫面

06 / INVISIBLE AUTOMATION

無感自動化規格

A. 智慧構圖

先顯示固定頭像／肩膀輪廓；在背景取得臉部位置，提供「位置大致正確」的視覺回饋。

  • 使用 AVCaptureMetadataOutput 的臉部中繼資料（metadataObjectTypes 設為 .face），由相機管線直接回報臉部矩形；不另接影格輸出，也不使用 Vision。
  • 用預覽層的座標轉換把臉部矩形換算成畫面座標，再與構圖區域比較。
  • 回呼頻率由系統決定；UI 狀態更新節流到每秒約 2–3 次，避免提示閃爍。
  • 只比較臉部 bounding box 與預設構圖區域，不辨識身份、不分析情緒。
  • 偵測不到臉時保持中性狀態，不要頻繁跳出警告。
  • 錄影中可停止更新構圖提示，優先確保錄影流暢。
  • 臉部框只是近似構圖輔助，不等於完整頭部／肩膀姿態估計。

B. 相機自動畫面

  • 優先使用 AVFoundation 支援的連續自動曝光、自動白平衡、自動對焦。
  • 不要一開始就自製 AI 曝光演算法，也不要持續覆寫原生自動控制。
  • 不保證自製 App 與 Apple 相機 App 的影像處理完全一致。
  • 若畫面明顯過暗，可提示使用者靠近光源；不要承諾相機參數能解決所有光線問題。
  • V1 不做美顏、磨皮、濾鏡商店或複雜色彩管線。

C. 收音檢查

  • AVAudioSession 只負責類別、路由與中斷處理。音量直接讀錄影輸出音訊連線的 audioChannels（averagePowerLevel／peakHoldLevel），不另開 AVAudioEngine，避免兩套音訊管線搶麥克風。
  • 以計時器每秒讀取約 10 次；錄影前與錄影中共用同一個來源。
  • 若真機上未錄影時讀不到音量，改在同一個 capture session 加 AVCaptureAudioDataOutput 計算能量；仍不使用 AVAudioEngine。
  • 顯示簡單的「收音正常」或「沒有偵測到聲音」提示。
  • 處理藍牙、外接麥克風、音訊路由變更與中斷。
  • 不把音量大小誤當成音質保證；V1 不做 AI 降噪或完整聲學診斷。

D. 陪伴人物的反應

  • 用收音檢查的同一個音量來源做能量門檻判斷說話／停頓，起始與結束各加延遲時間避免抖動；不需要語音轉文字或雲端 LLM。
  • 說話中：維持聆聽，偶爾輕微點頭。
  • 短暫停頓：保持眼神與自然表情，不急著反應。
  • 較長停頓：自然等待，不催促。
  • 待機片段準備 2–3 段，隨機輪播並交叉淡化，避免固定循環造成機械感。
  • 限制點頭頻率，避免每句話都點頭。
  • 角色不得發聲或打斷使用者；動畫只作為預覽 UI，不輸出到影片。
07 / TECHNICAL ARCHITECTURE

技術架構建議

模組建議技術責任
UISwiftUI拍攝畫面、文字稿、設定、完成頁、Overlay

音訊AVAudioSession＋錄影音訊連線的 audioChannels錄音路由、中斷處理、音量讀取、說話偵測輸入
陪伴角色AVPlayer 播放無音軌預錄短片（V1）；Rive／3D 待驗證後評估待機、點頭、微笑片段的切換與交叉淡化

設定保存UserDefaults記住畫質、提詞設定、頭像框大小等

建議程式模組

  • CameraService：AVCaptureSession、前鏡頭、錄影、格式、權限、中斷處理。
  • RecordingViewModel：錄影狀態與流程協調。
  • TeleprompterView／TeleprompterService：稿件顯示、滾動、暫停與位置。
  • ScriptEditorView：完整文字貼上與編輯。
  • FramingGuideView：固定構圖輪廓及狀態顯示。
  • FaceDetectionService：接收 AVCaptureMetadataOutput 的臉部矩形並換算座標，不處理影格。
  • CompanionModeView：預錄短片的播放與狀態切換。
  • SpeechActivityMonitor：讀取錄影音訊連線的音量，輸出收音狀態與說話／停頓，不做語意理解。
  • VideoReviewView：預覽、重拍、儲存。
  • SettingsStore：保存使用者偏好。
  • DebugOverlayView：隱藏手勢開啟的除錯資訊層。
重要實作提醒：AVCaptureSession、影格處理與錄影狀態應避免在主執行緒做重工作。臉部中繼資料的回呼處理不可阻塞錄影管線；必須在真機測試效能、掉幀、發熱與音訊同步。
08 / USER FLOWS

主要使用流程

提詞模式

開啟 App→貼上稿件→對準構圖框→開始錄影→提詞→預覽／儲存

陪伴模式

開啟 App→選陪伴模式→虛擬人物就位→開始錄影→自然說話→預覽／儲存

兩種模式共用 CameraService、錄影、儲存與基本相機控制；僅提詞／陪伴 UI 與狀態管理不同。

10 / ACCEPTANCE CRITERIA

驗收標準

  1. 首次開啟後，使用者能清楚理解如何授權相機與麥克風。
  2. App 開啟後直接進入拍攝主畫面，不需先穿越多層選單。
  3. 使用者能貼上完整稿件，文字不會被強制拆成逐句卡片。
  4. 提詞可調整大小、速度與透明度；錄影與提詞狀態彼此獨立。
  5. 構圖框只顯示在預覽畫面，不會出現在輸出影片。
  6. 能以裝置支援的格式錄製直式前鏡頭影片並儲存至照片圖庫。
  7. 錄影期間無明顯掉幀、聲畫不同步或異常發熱；需在多款實機測試。
  8. 臉部偵測失敗時 App 仍可正常錄影，不可將辨識設為錄影必要條件。
  9. 陪伴模式的動畫不會進入輸出影片，也不會搶占或中斷錄音。
  10. 使用者能在不閱讀長篇教學的情況下完成第一次錄影。
  11. 提詞時視線落在螢幕頂端；回看影片不會明顯看出眼神偏下。
  12. 除錯資訊層可由隱藏手勢開啟，顯示實際錄影格式、FPS、音訊路由與最近一次錯誤，內容可複製。
11 / RISKS & CONSIDERATIONS

技術風險與注意事項

  • 畫質：使用 Apple 原生相機硬體與 AVFoundation，但自製 App 不保證完全複製 Apple Camera App 的影像處理、HDR 或所有特殊功能。需明確測試支援機型與格式。
  • 4K：前鏡頭是否支援 4K、特定 FPS 與動態範圍依機型而異。UI 必須依實際可用格式呈現，不可硬編碼所有裝置都有 4K/60。
  • 直式影片：驗證方向 metadata、前鏡頭鏡像預覽與輸出方向，避免影片旋轉或左右方向錯誤。
  • 臉部偵測：臉部矩形不等於完整頭部輪廓；頭髮、帽子、側臉與光線會影響偵測。構圖提示應寬容，不要過度糾正。
  • 陪伴人物：動畫需克制。頻繁點頭、固定循環、錯誤時機的笑容可能造成反感。應提供關閉選項。預錄片段不得含音軌，避免播放時影響錄音工作階段。
  • 音訊：收音檢查與說話偵測共用錄影的音訊連線，不建立第二條音訊管線；仍需處理藍牙路由、來電、其他 App 音訊中斷等情況。
  • 開發環境：以 Windows 開發、沒有 Mac，建置與簽章全走雲端 CI，驗證只能在真機進行。每次迭代成本高，所以需要除錯資訊層把真機狀態帶回來。
  • 隱私：清楚說明臉部偵測與音訊活動分析用途；V1 不保存身份特徵、不上傳影像或語音內容。

13 / CLAUDE CODE HANDOFF

交給 Claude Code 的執行指示

請先閱讀整份規格，再開始修改專案。開發分兩輪：第一輪一次完成 P0、臉部定位、收音檢查與除錯資訊層，交付後由使用者在真機整體測試並回報；第二輪才做陪伴模式。開發環境是 Windows，沒有 Mac 與 Xcode，建置與簽章全部走雲端 CI。

任務順序

  1. 檢查現有專案、Bundle ID、部署目標與雲端 CI 設定；沒有專案就建立，並先確認 CI 能產出可裝到真機的版本。
  2. 建立 CameraService，先完成前鏡頭預覽、錄影與相簿儲存。
  3. 處理直式方向、鏡像預覽、輸出方向與中斷；加入除錯資訊層，讓真機上的格式、FPS、音訊路由與錯誤可被看見並複製回報。
  4. 再加入文件式文字稿編輯與提詞 Overlay。
  5. 加入固定頭像框，確認 Overlay 不會被錄進影片。
  6. 加入 AVCaptureMetadataOutput 臉部定位與收音檢查。
  7. 第一輪到此為止，交付真機測試。第二輪：新增 CompanionModeView、說話偵測與預錄短片切換。

實作規則

  • 每次交付都要通過雲端 CI 建置並能裝到真機。模擬器沒有相機，不作為驗收依據。
  • 不要為了架構過度抽象；但相機、提詞、構圖、陪伴動畫需保持模組分離。
  • 不要假設所有 iPhone 都支援相同的錄影格式。
  • 不要在主執行緒做相機設定、臉部回呼處理或音訊運算。
  • 遇到規格與 iOS API 能力不一致時，先回報限制與替代方案，不要假裝已完成。
  • 先交付可工作的 V1，再討論非必要功能。

第一輪完成定義

能在實機打開 App、看到前鏡頭、貼上文字稿、顯示提詞與構圖框、完成錄影，並將不含 UI Overlay 的影片存入照片圖庫；臉部定位提示與收音檢查可運作，除錯資訊層可開啟。
